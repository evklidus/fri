# Классификатор новостей (DeepSeek)

**Статус:** код в проде, включается ключом `DEEPSEEK_API_KEY`. Без ключа всё работает как раньше — на словарях.
**Добавлено:** 2026-09-25

## Какую проблему решает

Новости приходят из MediaStack по поиску имени игрока. Словарные фильтры, которые их чистили, ошибались тремя способами — все три партнёр видел в ленте:

1. **Однофамильцы и чужие истории.** Статья про Браима Диаса попадала к Луису Диасу. Список трансферов, где игрок назван одним из двадцати, считался новостью о нём.
2. **Неверный знак.** «Реал оштрафовал Вальверде» (*fine* — штраф) засчитывалось как позитив, потому что в словаре *fine* = «хорошо».
3. **Пропущенные события.** Удаления, дисквалификации, штрафы и награды попадали в **Vote on Events** только тогда, когда в заголовке стояло ключевое слово. Это редкость: открытых событий для голосования было 0.

Модель читает каждую новую статью (заголовок, начало текста, источник) и отвечает на три вопроса:

| Поле | Значения | Что делает |
|---|---|---|
| `about` | `subject` / `mentioned` / `other_person` / `not_football` | Отбирает статьи. `other_person` и `not_football` выбрасываются, `mentioned` идут после `subject` |
| `impact` | целое от −3 до +3 | Заменяет словарную тональность в Media Score |
| `event` | одно из 17 событий или `none` | Предлагает событие в Vote on Events (голосование 72 часа) |

Список событий и дельт один на оба бэкенда: `newsEvents` в [news_classifier.go](../internal/service/news_classifier.go). Там, например, `red_card` −1.5, `suspension` −2.5, `trophy` +4, `award` +3. Автоматически, без голосования, применяется только `serious_injury`.

## Как устроено

```
MediaStack → фильтр live-блогов → news_suppressions (удалённые модератором)
          → judgeArticles:  кэш вердиктов (article_verdicts)
                            ↳ новые статьи → DeepSeek → вердикты → в кэш
          → отбор (subject, потом mentioned) → лимит на игрока
          → Media Score (impact) + события → Vote on Events
```

- **Каждая статья оценивается один раз.** Вердикт сохраняется в `article_verdicts` по ключу статьи, и следующие синки берут его из кэша. Модели уходят только статьи, которых раньше не было.
- **Одно событие на статью.** Ключ события — `article:<ключ статьи>`, поэтому повторный синк не создаёт дубль.
- **Если DeepSeek недоступен**, неоценённые статьи в этом запуске пропускаются, а не оцениваются словарём наугад. Уже оценённые продолжают работать. Непроверенное доберётся в следующий синк (в проде раз в 12 часов, `MEDIA_SYNC_INTERVAL_MINUTES=720`).
- **Когда ключ задан, словарный поиск событий выключен**, чтобы одно событие не пришло дважды из двух источников.
- **Выбор бэкенда:** если задан `DEEPSEEK_API_KEY`, работает DeepSeek; иначе, если задан `ANTHROPIC_API_KEY`, работает Claude; если нет ни того ни другого, работают словари. Логика — `NewNewsClassifier` в [news_classifier.go](../internal/service/news_classifier.go).

Код DeepSeek-бэкенда: [news_classifier_deepseek.go](../internal/service/news_classifier_deepseek.go). Тесты: [news_classifier_deepseek_test.go](../internal/service/news_classifier_deepseek_test.go).

## Почему запрос выглядит именно так

Всё ниже взято из официальной документации DeepSeek (ссылки в конце) и её известных подводных камней.

| Решение | Почему |
|---|---|
| Прямой HTTP, без SDK | API DeepSeek совместим с OpenAI (`POST /chat/completions`). Готовые Go-клиенты есть: `openai/openai-go` с `WithBaseURL`, `sashabaranov/go-openai`, `cohesion-org/deepseek-go`. Но нужное нам поле `thinking` нестандартное, и в OpenAI-SDK его всё равно пришлось бы передавать через обходной механизм. Сотня строк на `net/http` проще лишней зависимости |
| Модель `deepseek-flash` | Рекомендованная DeepSeek модель, самая дешёвая. Для сортировки новостей её хватает. Меняется через `DEEPSEEK_MODEL` (например, `deepseek-v4-pro`) |
| `"thinking": {"type": "disabled"}` | У V4-моделей размышление включено по умолчанию. Для классификации оно не улучшает ответ, а выходных токенов тратит в разы больше |
| `temperature: 0` | В режиме без размышления температура работает. 0 даёт одинаковые вердикты от синка к синку |
| `response_format: {"type": "json_object"}` | JSON-режим DeepSeek. По документации он требует, чтобы в промпте было слово «json» и пример ответа, — оба есть |
| Проверка ответа в коде (`parseVerdicts`) | JSON-режим гарантирует валидный JSON, но **не** схему: поля и значения он не проверяет. Поэтому код сам проверяет, что на каждую статью пришёл ровно один ответ и `about` из списка. `impact` обрезается до ±3, выдуманное событие превращается в «нет события» |
| `max_tokens` = 400 + 150 × число статей | Известная проблема: ответ обрывается на лимите посреди JSON (`finish_reason: length`). Запас в 2–3 раза от реального ответа |
| 3 попытки с паузой | Повторяются пустой ответ (задокументированный сбой JSON-режима), `length`, `insufficient_system_resource`, HTTP 429/500/503 |
| Без повторов при 400/401/402/422 | Неверный запрос, неверный ключ, кончился баланс. Повтор не поможет, ошибка сразу уходит в лог |
| Системный промпт неизменный, события отсортированы | У DeepSeek автоматический кэш префикса: одинаковое начало запроса стоит в ~50 раз дешевле. В логе видно `N prompt tokens (M cached)` |

## Сколько стоит

Цены DeepSeek на сентябрь 2026 за 1 млн токенов для `deepseek-flash`: вход $0.15–0.30 (из кэша $0.003–0.006), выход $0.60–1.20. Вне пиковых часов — половина цены.

Один вызов — это один игрок и до 5 новых статей: ~1 700 токенов на вход, ~300 на выход. Худший случай — у всех 100 игроков новые статьи на каждом синке (раз в 12 часов), то есть 200 вызовов в сутки: **около $0.1 в день, до ~$3 в месяц**. На деле меньше: большинство статей уже в кэше вердиктов.

Первый запуск разово оценит все текущие статьи 100 игроков — это ~100 вызовов, центы.

DeepSeek работает по предоплате: когда баланс заканчивается, API отвечает 402. Классификатор тогда просто перестаёт оценивать новые статьи, а в логе появляется `http 402`.

В DeepSeek уходят только публичные заголовки и анонсы новостей плюс имя, клуб и позиция игрока. Данных пользователей там нет.

## Как включить

1. Зарегистрироваться на [platform.deepseek.com](https://platform.deepseek.com), пополнить баланс (хватит $5–10) и создать ключ в разделе **API Keys**.
2. На сервере дописать в `/opt/fri/deployments/.env`:
   ```
   DEEPSEEK_API_KEY=sk-...
   ```
3. Пересоздать приложение, чтобы оно подхватило переменную:
   ```bash
   cd /opt/fri/deployments && docker compose -f docker-compose.prod.yml --env-file .env up -d app
   ```
4. Запустить медиа-синк из админки или дождаться планового. Проверить:
   ```bash
   docker logs fri-app 2>&1 | grep "news: deepseek" | tail
   ```
   Ожидаемо: строки вида `news: deepseek 5 articles, 1712 prompt tokens (896 cached), 284 out, finish stop`.
   Вердикты копятся в БД: `SELECT count(*) FROM article_verdicts;`.

**Выключить:** убрать строку из `.env` и повторить шаг 3. Вердикты в кэше не мешают: без классификатора они просто не читаются.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DEEPSEEK_API_KEY` | пусто | Включает классификатор |
| `DEEPSEEK_MODEL` | `deepseek-flash` | Модель |
| `DEEPSEEK_BASE_URL` | `https://api.deepseek.com` | Для прокси или совместимого провайдера |

## Что смотреть, если что-то не так

- `news: classifier failed for X: deepseek: http 401` — неверный ключ.
- `... http 402` — кончился баланс.
- `... 3 attempts: empty content` — DeepSeek несколько раз подряд вернул пустой JSON. Статьи оценятся в следующий синк.
- Модель ошиблась со статьёй — модератор удаляет её через админку, как раньше (`news_suppressions`). Удалённая статья больше не участвует ни в счёте, ни в событиях.
